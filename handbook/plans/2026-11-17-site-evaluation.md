**2. 复杂度控制原则**

1. 每批最多 3 个任务，每项有独立验收；仅有依赖的任务等待前置完成。
2. 只读在前、变更在后；已完成的机器检查与有限抽审复用证据，E 只计划本地改动，不部署、不改云端。
3. 不新增平台依赖：能用现有 `tools/checks/`、`tests/browser/`、Playwright、axe-core 完成的，不引入新的 SaaS 或账号。
4. 内容改动与安全改动分开提；机器可验证的修复必须带回归测试。
5. **结论力度与证据相称**：命令退出 0 ≠ 质量达标；自动化代理走查 ≠ 真人可用性；实验室 LCP ≠ field CWV；安全头齐全 ≠ 安全通过。任一条被违反，报告结论降级为局部诊断。

**3. 六维记分卡（候选规则，尚未启用）**

以下权重与公式仅保留作后续评分设计。指标清单、分母、逐项评分锚点与适用性须在下一轮采样前冻结；现有通用描述不足以直接评分，不以既有结果倒推评分规则。本轮只交付证据覆盖、缺陷状态与待办，不发布总分或等级。

**评分与未知规则**：0＝有证据证明关键能力缺失或阻断；1＝核心能力有重大缺陷；2＝基础能力可用但有明确缺口；3＝固定样本通过且无重大缺陷；4＝固定样本、人工任务和相关边界均有可复核证据且通过。未知记 `U`，不适用记 `N/A`，均不等于零分。维度分 `D = 25 × 已核适用指标分数之和 / 已核适用指标数`；覆盖率 `C = 已核适用指标数 / 全部适用指标数`，二者同时披露。

**判定规则（v3 起沿用）**：

- **表述口径不算知识错误**：检查器对「常考／高频」类表行的告警，先分「频率声称（需统计范围与题号依据）」与「题型建议（按建议语义改写即可）」两类，只有前者计入内容维度缺陷；计数时写明是「缺证据的声称行」，不写成知识错误数。
- **验证缺口单列**：真人可用性、读屏听测、源站访问边界属必要指标，未核时该维度只给 `U` 与局部诊断；缺口本身不判为已确认故障，也不折算成扣分。必要指标未核或任一维覆盖率低于 80% 时，不发布全站总分、等级或「通过」。

**6. E 阶段：分三批的本地收口计划**

原 E1–E3 的「按 P0→P1→P2 顺序修」过于笼统。v4 按批组织，每批不超过 3 项，各项有独立验收；无依赖者可同批并行，有依赖者等前置验收后再动。任务编号按批次顺序重排（第 1 批 E1–E3，第 2 批 E4–E5，第 3 批 E6–E7），其中 E3 为按条件触发的安全复核。

**第 1 批：发布链与现状复核（互不依赖，可并行）**

- **E1 CI 安装顺序（P1 配置隐患，0.25 人日）**：`.github/workflows/ci.yml:31–38` 先跑 `npm run check`（链内含 `check:a11y`、`check:layout` 等需浏览器的任务），再执行 `npx playwright install --with-deps chromium`。改为「装依赖 → 装浏览器 → `npm run check` → `test:browser` → `test:search`」，失败即停。本机有 Playwright 缓存，故未复现干净 runner 上的失败；不把它写成已确认的线上故障。验收：使用全新的临时 `PLAYWRIGHT_BROWSERS_PATH` 或干净 runner／容器，先记录旧顺序是否复现缺浏览器，再验证新顺序全链退出 0；不删除本机共享缓存，Windows 本地结果也不等同于 Ubuntu CI 验证；若 `check` 内确有任务不需浏览器，可另拆 job 缩短时长，不作前置。
- **E2 声称行三类清单（P1 的第一步，0.25 人日）**：只导出不修改。把检查器命中的 765 条按「频率声称／题型建议／其他统计」分类，输出 CSV 到 `artifacts/`（不进仓库），并统计各类占比与集中在哪些章节。验收：清单可复算（脚本＋命令留档），三类边界有判定说明，能回答「765 条里真正需要证据的是多少」。
- **E3 安全三项条件复核（预留 0.25 人日，公网可见面）**：本日已有 E06 响应头证据，默认复用；仅在发布／配置变更、证据缺字段或独立安全整改前触发复测。触发后复测 CSP `unsafe-inline`、HSTS `max-age=2592000`、ESA `Set-Cookie`（`acw_tc`／`cdn_sec_tc`）缺 `Secure`／`SameSite` 的当前值。验收：一张「项—当前值—证据—与 11-16 差异」表，只填实测项；源站回源收敛与速率规则维持观察态，不在本轮变更。

**第 2 批：内容治理（依赖 E2 清单）**

- **E4 频率声称的改文（P1，1.0–1.5 人日）**：对清单里的「频率声称」逐条处理：有统计范围（哪些卷、年份区间、样本量）与题号依据的补锚点；无依据的改为题型建议语义或删除表述。不批量贴「看起来像」的题号。验收：改动清单逐条对应原句与处理方式，`check:content` 通过，`--strict` 剩余告警有台账解释。
- **E5 检查器「统计范围必填」规则（P2，0.5 人日）**：在 `exam_claims.py` 增加声称类型判定与统计范围必填两条规则，附单元测试；默认告警与 `--strict` 的边界保持显式；历史声称同样进入分类台账，暂缓项附理由，不静默豁免。验收：误报、漏报与统计范围缺失各有红—绿回归测试，默认全链退出 0，`--strict` 剩余项逐条可解释；告警减少本身不作为质量通过的证据。

**第 3 批：搜索与性能（依赖第 2 批稳定后的构建产物）**

- **E6 搜索召回专项（P2，0.5 人日）**：针对 21/507（4.1%）正文—索引丢失对，先比较正文与生成索引以定位覆盖损失，再独立检查面板分词与排序；权重不作为索引文本缺失的直接归因；优先保证术语、标题、概念定义可检索，再谈截断阈值。验收：丢失对降到可解释范围，或每条剩余丢失有书面理由；`test:search` 与 `measure:search` 基线同步更新。
- **E7 性能串行复测（P2，0.25 人日）**：移动 LCP 三个贴线样本（OS 2 588 ms、CO 2 704 ms、术语表 2 508 ms）在无并行负载、串行三轮下重测并记录离散度。验收：复测表含均值与方差，结论区分「观测」与「归因」；未定位到具体耗时源前不提优化方案。

**7. F 阶段：验证补测（需真人，不可由代理替代）**

- **F1 真人可用性测试（0.5 人日）**：2–3 名目标读者完成 C1 的五条任务，记录完成率、卡点与耗时。C1 的 `pass-automated-proxy` 结论只作前置筛选，不替代本项。
- **F2 读屏听测（0.5 人日）**：用 NVDA 或讲述人读一章正文、一个练习与一次搜索，检查朗读顺序、标题层级播报、错误提示可闻性；与 axe 的 70 条 incomplete 对账。
- 验收：两项各出一份记录；发现的问题进台账并按 P1/P2 分级，未发现则明确写「未复现」，不写「通过无障碍」。

**8. G 阶段：阻塞项**

- **G1 源站内部配置复核**：`nginx -t`、回源校验文件权限、`certbot.timer` 状态、安全组与回源白名单。前置是 `.env.local` 中有可用的 `STUDY_ECS_INSTANCE_ID`（上次核对时缺失，本次未重查）。在此之前，报告中相关项一律记「未核」，不得写成「已核」或「通过」。

- 边缘证书 2027-02-02 到期，距今约 76 天；复测须记录剩余天数，续期异常升 P1。
- 修改 `docs/` 或 `handbook/` 文字后须刷新 `config/content-rights.json` 的 `sha256`（本方案改动同样适用），否则 `rights.py` 报 `changed since rights review`。
- 抽审引用的教材原文只作核对依据，不进仓库、不进报告正文。
- CI 验证使用隔离浏览器目录或干净 runner／容器，不清理共享缓存；Ubuntu runner 的系统依赖与 Node 22 环境需单独确认。
- 验收失败只回退本任务的差异，保留其他已存在的工作树改动；本次计划调整不执行回退或实现操作。

**14. 验收与回退**

- 每个任务只认一个验收口径，写在前面对应任务里；同批任务完成后再进下一批。
- E 阶段每项改动前记录现状（命令与输出），改动后复测同一命令，失败即回退到记录值。
- 报告一旦发布即为当轮结论快照；后续轮次另起 `-results` 文件，不覆盖历史结论。
